# Behaviour spec: tasks-git helper

Scope: `plugins/tasks-ledger/scripts/tasks-git.js`. This spec also owns the glob-overlap block, which
must appear byte-identical in `workflows/tasks-engine.js`.

Tests live in `plugins/tasks-ledger/tests/`:

| Short name | File |
|---|---|
| `eng` | `tasks-engine.test.mjs` |
| `led` | `tasks-git-ledger.test.mjs` |
| `pr` | `tasks-git-prs.test.mjs` |
| `prep` | `tasks-git-prepare.test.mjs` |
| `sb` | `helpers/git-sandbox.mjs` |
| `tk` | `tasks-git-tasks.test.mjs` |

## Purpose

The tasks workflow cannot touch files. It delegates every repository, worktree and ledger mutation of
a run to this command-line program and reads back one JSON answer per call.

## Interface

**Invocation.** `node tasks-git.js <command> <ledger> [args...]`.
- `<ledger>` must be a file directly inside `<repo>/.claude/runs/`.
- The repository root is the parent of that `.claude` directory.

| Command | Arguments after `<ledger>` |
|---|---|
| `finish` | `<runStatus> [reason]` |
| `merge` | `<id>` |
| `prepare` | `<runId> [takeover]` |
| `prs` | none |
| `status` | `<id> <status> [evidence]` |
| `sync` | none |
| `verify` | `<id>` |
| `worktree` | `<id>` |

**Answer.**
- Every invocation prints exactly one JSON line to stdout and exits 0, failures included
  (sb:117-123).
- Success answers carry `ok: true`. Failure answers carry `ok: false` and an `error` string; some
  carry extra fields named below.

**Files next to the ledger `<name>.json`:**

| File | Role |
|---|---|
| `<name>.inbox.jsonl` | tasks submitted during a run, one JSON object per line (sb:112) |
| a file whose name contains `.inbox.jsonl.ingested-` | the consumed inbox, kept (led:65) |
| `<name>.lock` | run lock, a JSON object with `runId` and `at` (epoch ms) (sb:111, prep:41) |

**Forge CLI override.**
- `TASKS_GIT_GH` replaces `gh`, and `TASKS_GIT_GLAB` replaces `glab`.
- Each holds a `|`-separated program plus leading arguments, as the test sandbox sets them
  (sb:47-55).

**Names.** `<topic>` is the ledger's `topic` and `<root>` the repository root.

| Thing | Name |
|---|---|
| integration worktree | `<root>/.claude/worktrees/<topic>-integration` |
| task worktree | `<root>/.claude/worktrees/<topic>-<id>` |
| integration branch | `task/<topic>/integration` |
| task branch | `task/<topic>/<id>` |
| combined prerequisites, only for tasks with two or more | `task/<topic>/<id>-base` |

**Ledger task keys.** A stored task may carry only these 14 keys: `acceptance`, `base`, `branch`,
`budget`, `constraints`, `dependsOn`, `evidence`, `files`, `id`, `pr`, `proof`, `status`, `title`,
`worktree`. The schema written separately describes the same set; this list is authoritative for the
helper.

## Behaviour

### Properties shared by all commands

- **Unknown ids.** An unknown task id gives `no task <id>` (tk:33, tk:160).
- **Rejected or empty commands.** A rejected command leaves the ledger unchanged (tk:155-167), and
  one that changes nothing leaves it byte-identical (led:84-87).
- **Ledger writes are atomic.**
- **Task listing.** The `tasks` arrays in answers list every ledger task in ledger order. Each entry
  has `acceptance`, `base`, `branch`, `budget`, `constraints`, `dependsOn`, `files`, `id`, `pr`,
  `proof`, `status`, `title` and `worktree`. In the answer only, missing lists become `[]` and
  missing scalars `null`. Key order is free.
- **Shell checks** are the ledger's `setup` and `suite` and the trimmed content of
  `.claude/verify.cmd`.
  - A failure answer includes `tail`, the end of the check's output.
  - They run in bash inside the relevant worktree. The time limit is `checkTimeoutMin` minutes when
    set, otherwise a default.
- **Start ref.** `origin/<baseBranch>` when it exists, otherwise the local `<baseBranch>`.

### finish `<runStatus> [reason]`

- **Accepted values.** `finished`, `running`, `stopped`. Anything else fails with
  `bad runStatus <value>` and keeps the lock (led:111-118).
- **Effect.**
  - The lock file is removed.
  - `runStatus` takes the value, and `stopReason` takes the reason or `null`.
  - Answer: `{ ok, runStatus, tasks }` (led:93-109).

### merge `<id>`

- **Success answer.** `{ ok, id, sha }`, where `sha` is the short HEAD of the integration worktree
  (tk:178).
- **Refusals that change nothing:**
  - no worktree has `integrationBranch` checked out: `integration worktree missing` (tk:245-250);
  - the task is not `verified`: `<id> is <status>, only verified tasks merge` (tk:188-197).
- **Normal merge postconditions:**
  - the commit's subject is `merge <id>: <title>`;
  - tracked files are clean;
  - the task branch reached the integration branch through exactly one merge commit (tk:171-186).
- **Dirty integration worktree.** Only changes to tracked files can block a merge. Untracked files in
  the integration worktree (for example left by `setup`) do not (tk:171-186).
- **Combined checks.** Before the merge commit is made, the merged tree must pass each present one of
  `setup`, the integration worktree's verify command and `suite`.
- **Evidence.** The task becomes `merged`. Its evidence matches
  `^<old evidence> \| merged into <integrationBranch> @ <sha>; checks: ` (tk:184).
- **Already merged.** When the integration branch already contains the task branch:
  - the answer has `already: true`, and its `sha` is the integration worktree's short HEAD, the
    same value the original merge reported (tk:239);
  - the task becomes `merged`, and its evidence gains `already in <integrationBranch> @ <sha>`;
  - no new merge is made (tk:230-243).
- **Failed combined check.**
  - Error: `<id>: combined check failed after merging (<command>, exit <code>); merge aborted`.
  - Tracked files are clean and HEAD is unchanged (tk:216-228).
- **Merge conflict.**
  - Error: `<id> conflicts with already-merged tasks`.
  - The task stays `verified`. The integration worktree's HEAD is unchanged, and it has neither
    changes nor a merge in progress (tk:199-214).

### prepare `<runId> [takeover]`

**Success answer** (prep:31-40; key order is free):
- `added`: ids ingested from the inbox;
- `integration`: the integration worktree's path (not the branch name);
- `prs`: the ledger's `prs` as a boolean;
- `root`: the repository root;
- `start`: the start ref;
- `tasks`: the task listing;
- `warnings`: an array of strings.

**Postconditions on success:**
- The lock holds this `runId` (prep:41-42).
- Ledger: `runStatus` is `running`, `stopReason` is `null` and `integrationBranch` is set
  (prep:43-46).
- Statuses: `in_progress` and `done` become `todo`; all others stay (prep:69-75).
- The inbox has been ingested as described under `sync`, and `added` lists the new ids
  (prep:129-135).
- The integration branch exists with its worktree at the standard path, and the ledger's `setup`
  (if any) has run there (prep:32-37).
  - On a first call the branch starts from the start ref.
  - On a repeated call an existing integration branch and worktree are reused as they are; the branch
    is never reset (prep:57, led:105).
- `warnings` is empty for a clean repository whose ledger has a `setup`, whose worktrees directory
  is git-ignored, and whose tasks have no unlinked overlaps (prep:38).

**Warnings.** Each condition below adds one warning string; the call still succeeds. Rows are in
alphabetical order of the condition.

| Condition | Warning contains |
|---|---|
| `.claude/worktrees/` is not git-ignored | `not gitignored` (prep:92-96) |
| the ledger has no `setup` | ``no `setup` command`` (prep:77-81) |
| two tasks overlap without a dependency link | see Overlap warnings |

A failed fetch from `origin` may add a warning as well.

**Failures.** An invalid `runId` is rejected before anything else happens; the order of the other
checks is free. Rows are in alphabetical order of the error text.

| Condition | Error contains | Extra |
|---|---|---|
| the lock holds a different, live `runId`, and no `takeover` argument was given | starts with `another run (<held runId>` (prep:49-60) | `locked: true` |
| `runId` does not match `^[A-Za-z0-9-]{4,64}$` | `runId` (prep:62-67) | |
| `setup` exits non-zero | matches `setup .* failed .* exit <code>` (prep:83-90) | `tail` |
| `.claude/verify.cmd` is not in the main checkout's git index (a copy on the start ref does not count) | `verify.cmd is not tracked` (prep:98-106) | |

**Lock rules.**
- A lock is live while its `at` is less than six hours old; an older one is stale and may be replaced
  without `takeover`. `sync` refreshes `at`.
- `takeover` replaces a live foreign lock (prep:58-59).
- The same `runId` never conflicts with itself (prep:57).
- A lock refusal leaves the existing lock untouched.
- When the call fails for any other reason, no lock of this call remains afterwards (prep:83-106).

**Overlap warnings.**
- They are computed after the inbox has been ingested, so newly added tasks take part
  (prep:129-135).
- Each pair of tasks with overlapping `files` (by `globListsOverlap`) gets a warning when neither task
  reaches the other through `dependsOn`, transitively.
- The warning begins with `<first> and <second> have overlapping files globs`, the earlier ledger
  task first (prep:8-13).
- Disjoint tasks give none (prep:123-127).
- Required result (prep:108-121): for T1 `src/**`, T2 `src/a.js`, T3 `src/b.js` (depends on T1),
  T4 `lib/**`, T5 `src/c/**` (depends on T3) and T6 `**/*.md` (depends on T5), the reported pairs
  are exactly T1+T2, T2+T6 and T4+T6.

### prs

- **Refusal.** When the ledger's `prs` is not true, the error contains `prs is false`, nothing is
  pushed and no CLI runs (pr:53-62).
- **Success answer.** `{ ok, results }`.
  - A task that already has a `pr` contributes `{ id, pr, skipped: "exists" }` and causes no CLI
    call (pr:47-50).
  - Each newly opened request contributes exactly `{ id, pr, target }`, where `target` is the
    task's base (pr:39-44).
- **Which tasks.** Only `merged` tasks get requests, prerequisites before dependants.
  - A pushed task branch on `origin` equals the local one (pr:26).
  - A stacked task's `-base` branch is pushed as well, because it is that request's target.
  - Nothing else is pushed: not the integration branch, and no branch or `-base` branch of a task that
    is not merged (pr:22-26).
- **Forge.**
  - An `origin` URL containing `gitlab` uses `glab mr create --draft` with `--source-branch` and
    `--target-branch` (pr:85-100).
  - Any other origin uses `gh pr create --draft` with `--head`, `--base`, `--title` (the task title)
    and `--body` (pr:28-36).
  - A stacked task targets its base (pr:36, pr:98).
- **Request text.** It contains `**<id>: <title>**` (pr:34). For a task with prerequisites it also
  contains `Stacked on <dep> (<dep's request URL>)` (pr:37). Everything else in the text is free.
- **Request URL.** It is read from the CLI output and stored in the task's `pr` (pr:43-44).
- **CLI failure** (non-zero exit or no URL found):
  - error: `<gh|glab> <pr|mr> create failed for <id>: <output>`, where `<output>` is the CLI's
    stdout and stderr combined (pr:75-83);
  - that task's `pr` stays unset;
  - the answer includes the `results` collected so far.

### status `<id> <status> [evidence]`

- **Answer.** Exactly `{ ok, id, status }` (tk:145).
- **Evidence.**
  - Leaving it out keeps the stored evidence (tk:148-150).
  - Evidence that is given is stored, cut to 4000 characters (tk:151-152).
- **Settable values.** `blocked`, `done`, `in_progress`, `todo`, `verified`. Any other value,
  `merged` included, fails with `status <value> not settable` and changes nothing (tk:155-167).

### sync

- **Answer.** `{ ok, added, tasks }`.
- **Lock refresh.** An existing lock gets `at` set to now and keeps its `runId` (led:88-90).
- **Without an inbox.** `added` is `[]` and the ledger stays byte-identical (led:80-87).

**Inbox ingestion** (also used by `prepare`; led:10-78):
- **Stored entry.**
  - `branch`, `base`, `worktree`, `pr` and `evidence` are `null`, and `status` is `todo`.
  - `files` is an array of strings, so `7` becomes `"7"`.
  - `dependsOn` keeps only entries matching `^T[0-9]+$`.
  - Keys outside the 14 ledger task keys are dropped.
  - `files` and `dependsOn` are always stored as arrays, empty when the line had none (led:58-62).
    Other optional keys the line did not have stay absent; the stored object for the T9 example is
    pinned exactly (led:45-57).
- **Ids.**
  - An entry whose `id` matches `^T[0-9]+$` and is not yet taken keeps it.
  - Any other entry gets a fresh, unique `T<n>`, counting up from the highest id the ledger held
    before this ingestion.
  - Example (led:71-78): an explicit T4 followed by three entries without id gives
    `[T4, T3, T5, T6]`.
  - Example (led:41): a ledger with T1 and T2 and an inbox holding the entries T9, T1, (no id),
    `../x`, `T1;rm` and one CRLF entry without id gives `added = [T9, T3, T4, T5, T6, T7]`.
- **Accepted lines.** Both LF and CRLF endings work. A line is skipped when it is not a JSON object
  or has no `title`.
- **Order.** New tasks are appended in the order of their inbox lines.
- **Consumption.** Afterwards the inbox file is gone, a renamed copy whose name contains
  `.inbox.jsonl.ingested-` exists, and a second `sync` adds nothing (led:64-68).

### verify `<id>`

- **Success answer.** `{ ok, id, commits, verify: "passed", tail }`, where `commits` counts the
  commits beyond the task's base (tk:120-129, tk:131-139).
- **Base used for counting.**
  - A task based on another task's branch, or on a `-base` branch, counts from that branch.
  - A task based on `baseBranch` counts from the start ref (`origin/main` in the tests).
- **Failures.** A missing worktree is reported first; the order of the rest is free. After that
  first row, rows are in alphabetical order of the error text, placeholders ignored.

| Condition | Error contains | Extra |
|---|---|---|
| no worktree on record or on disk | `worktree for <id> missing` (tk:114-118) | |
| no commits | `<id>: no commits on <branch> beyond <base ref>` (tk:83-90, tk:136) | |
| uncommitted changes, untracked files included | `uncommitted changes` (tk:92-102) | `dirty`, porcelain lines |
| the verify command fails | `verify.cmd exited <code>` (tk:104-112) | `tail` |

- The ledger is not written.

### worktree `<id>`

- **Answer.** Exactly `{ ok, id, branch, base, worktree }` (tk:17). The ledger task then has
  `status` `in_progress` and the same `branch`, `base` and `worktree`.
- **Refusal.** Every prerequisite must be `merged`. Otherwise the error is
  `prerequisite <dep> is <status>, not merged` (tk:27-34).
- **Idempotence.** Repeating the command returns the same answer; the worktree's commits, the `-base`
  branch and the worktree list stay as they were (tk:61-79).
- **Where the branch starts:**

| Prerequisites | `base` | Branch starts at | Test |
|---|---|---|---|
| two or more | `task/<topic>/<id>-base` | a branch containing every prerequisite branch, each joined by a real merge commit | tk:46-59 |
| one | that task's `branch` | that branch | tk:36-44 |
| none | the `baseBranch` name | the start ref | tk:13-25 |

- **The `-base` branch** in the first row:
  - if the prerequisites conflict with each other, the command fails and no `-base` branch is left;
  - afterwards no worktree of it exists (tk:59);
  - the last prerequisite is its second parent (tk:56).

### The glob-overlap block (owned here)

**Placement and form.**
- `tasks-git.js` and `tasks-engine.js` each contain a region that opens with a line consisting of
  `// BEGIN glob-overlap` and closes with a line consisting of `// END glob-overlap` plus a newline.
- With CRLF converted to LF, the two regions are identical (prep:15-27, eng:15).
- The region defines `globsOverlap(a, b)` and `globListsOverlap(as, bs)`. Evaluated alone in an
  empty `vm` context, it must make both names available (eng:22-27).
- It is self-contained, and outside whole-line `//` comments it contains no `import` and no
  `require(`.
- It must run unchanged both inside a CommonJS script and inside an async function body with the
  parameters `args`, `agent`, `phase` and `log`. So it declares none of those four, and neither host
  file redeclares a name the region declares.

**Required examples** (eng:32-72). "Both ways" means `globsOverlap` gives the same answer with the
arguments swapped.

| Patterns | Result |
|---|---|
| `Src/A.js` and `src/a.js` | overlap |
| `src/../lib/x`, `src/**/../../lib/x` or `../x` with anything | overlap |
| `src/@(x)/y` and `src/x/y` | overlap |
| `src/+(a|b).js` and `src/a.js` | overlap |
| `/src/a.js` and `./src/a.js` | overlap |
| `src//a//` and `src/a/b.js` | overlap |
| `src\a.js` and `src/a.js` | overlap |
| `./src/` and `lib/x` | disjoint |
| `./src/` and `src/x` | overlap |
| `**/*.md`, `{a,b}/x` or `!src/**` with anything | overlap |
| `src/ab.js` and `src/a` | disjoint |
| `srcx/**` and `src/**` | disjoint |
| `src/**` and `lib/**` | disjoint |
| `src/a.js` and `src/b.js` | disjoint |
| `src/*.js` and `src/a.js` | overlap |
| `src/**` and `src/a/b.js` | overlap |
| any pattern with itself, including `''` | overlap |

**Soundness.** "Disjoint" is reported only when no path can match both patterns (eng:81-105). Reporting
an overlap that does not exist is acceptable.

**Lists.** `globListsOverlap` is false for an empty or missing list, and otherwise true exactly when
some pair overlaps (eng:74-79).

**Rule that satisfies the table.**
- Normalise each pattern: lower-case it, read `\` as `/`, and drop empty and `.` segments.
- Any pattern with a `..` segment overlaps everything.
- Keep only the literal prefix of each pattern: its segments up to, not including, the first segment
  that holds a glob character. Glob characters are `*`, `?`, brackets, braces, extglob parentheses
  and a leading `!`.
- Two patterns are disjoint only if their prefixes disagree at some position where both have a
  segment.

## Errors

Rows are in alphabetical order of the condition.

| Condition | Error contains |
|---|---|
| ledger names unsafe for paths or git: `topic` not matching `^[a-z0-9][a-z0-9-]*$`, a task id or prerequisite not matching `^T[0-9]+$`, or a `baseBranch` that starts with `-`. Checked before any file or git action; nothing is touched | free text |
| ledger outside the runs directory | `not in <repo>/.claude/runs/`, where `<repo>` is literal text and not replaced by the path (prep:137-145) |
| no command or no ledger | `usage` (prep:149) |
| unexpected exception | an `ok: false` answer, still with exit 0 |
| unknown command `x` | `unknown command x` (prep:150) |
| unreadable ledger | `cannot read ledger` (led:120-126) |

## Security

**Push allow-list.** Before any push or CLI call, a branch is refused with `refusing to push`
unless it meets every condition:
- it is a well-formed branch name, so it has no colon and no whitespace;
- it is neither a permanent branch nor the integration branch. The integration branch is always
  the derived name `task/<topic>/integration`, whether or not the ledger records
  `integrationBranch` (pr:64-73 runs without `prepare`);
- it lies under `task/<topic>/`.

Tested cases (pr:64-73): `task/<topic>/T1:refs/heads/main`, another topic's branch, `main`, and the
integration branch.

**The user's checkout is left alone.** The helper works only in its own worktrees. The branch and
files of the main checkout never change.

**Untrusted ledger names.** `topic`, task ids, prerequisites and `baseBranch` become parts of paths
and git arguments, so a ledger whose names fail the checks in the Errors table is refused before
anything happens.

**Untrusted inbox.** Inbox lines may come from anyone who can write the file. Only `T<n>` ids and
prerequisites are accepted, and fields that the run itself manages are reset (led:10-62).

**One run per ledger.** At most one live run holds a ledger.

**No merges upstream.** The helper never merges a request and never pushes the integration branch.

- **Guard breaking limit (rev 10).** Without an atomic compare-and-rename, two breakers that judge the
  same crash-left guard abandoned at the same instant can both proceed. This needs a crash plus two
  callers within microseconds, and is accepted.

- **Guard release limit (rev 10).** A holder that keeps the guard for longer than 10 minutes can be
  broken between its own token check and the removal on release. Guarded steps take milliseconds, so
  this needs a stalled process, and it is accepted.

## Amendments (rev 4)

These amendments take precedence over the sections above where they differ.

1. **Inbox ids.** An inbox id with more than nine digits counts as invalid, and the line gets a
   freshly generated id. Every generated id has the form `T<n>`. Ingesting the inbox always
   terminates.
2. **Run lock.** Taking the lock is atomic: when several `prepare` calls with different run ids race,
   exactly one succeeds and every other one fails with a message containing `another run (`. When
   `prepare` fails, the lock that was there before the call is restored; if there was none, none is
   left behind.
3. **Changed `verify.cmd`.** `verify` and `merge` refuse a task whose branch modifies
   `.claude/verify.cmd` compared with the task's base. The refusal tells the user to change
   `verify.cmd` outside a run.
4. **Parent segments in globs.** A pattern that contains `..` anywhere, not only as a complete path
   segment, overlaps every other pattern. Both copies of the glob-overlap block (helper and engine)
   stay byte-identical.
5. **`prs` targets.** A PR target that is neither the ledger's `baseBranch` nor a well-formed
   `task/<topic>/` branch is refused with a message containing `refusing to push`.

## Amendments (rev 5)

1. **One lock owner, also from a stale lock.** Every step that reads the run lock, decides whether it
   may be replaced and writes a new one runs under a short exclusive guard, so at most one caller is
   in that step at a time. No caller ever moves or deletes a lock it has not judged replaceable. Of N
   concurrent `prepare` calls with different run ids exactly one succeeds, whether they start with no
   lock, a stale lock, or a lock that a `takeover` replaces. A guard left behind by a crashed caller
   does not block forever: it is considered abandoned after a short, fixed time.
2. **Lock refresh.** `sync` refreshes the lock's time under the same guard, and only when the lock
   still names the run that calls `sync`; it never writes another run id over a newer owner.
3. **Tests.** Race tests start from a stale lock and from a fresh lock with `takeover`, and assert
   that exactly one of the racing calls holds the lock afterwards.

## Amendments (rev 7)

1. **`finish [runStatus] [reason] [runId]`.** When a run id is given, `finish` removes the lock only
   when it names that run; a lock of another run is left in place. Without a run id it behaves as
   before. The Interface table lists `sync [runId]` and the new `finish` argument.
2. **`sync` without a run id** never refreshes the lock.
3. **Guard wait timeout.** When waiting for the guard times out, the error message also contains
   `another run (`.
4. **Withdrawn: amendment 2.** A kept test pins that a `sync` without a run id refreshes the lock, and
   the engine always passes its run id since engine rev 6, so only manual calls are affected. It is
   tracked as a follow-up. An empty `finish` reason is treated as no reason.

## Amendments (rev 8)

1. **Empty reason.** A missing or empty `finish` reason stores `stopReason: null`.
2. **Superseded `finish`.** When `finish` gets a run id and the lock names another run that is still
   live, `finish` changes nothing (ledger and lock stay byte-identical) and fails with a message
   containing `another run (` and `locked: true`. The decision is made under the guard, before
   anything is written.
3. **Racing takeovers.** Of N concurrent `prepare … takeover` calls with different run ids over a
   fresh lock, exactly one holds the lock afterwards and every other one fails with `another run (`.

10. **Every failed restore keeps the original error, and truncation never cuts another writer's lines.**
    This sharpens amendment 8.
    - When a failed `prepare` has no backup and restoring the lock fails for any reason (the guard wait
      ran out, `cannot create guard`, a failed rewrite or removal), the error is the original error
      followed by `; ` and the restore error. When the lock still holds this call's text, or restoring
      could not find out because the guard was not taken, `; the lock still holds this call's text` is
      added. The restore error never stands alone, and the answer keeps the original error's `locked`
      value.
    - Before truncating the inbox after a failed carry-over write, the helper takes the size again with
      `fstat` on the same descriptor. It truncates only when that size equals the recorded size plus the
      bytes this call wrote. Otherwise it leaves the file as it is and gives the warning ending in
      `; the inbox may hold part of these lines`.
