# Behaviour spec: handover plugin

Files to write, under `plugins/handover/`:
- `hooks/hooks.json`, `hooks/session-start-context.js`, `scripts/fresh-marker.js`;
- `skills/handover/SKILL.md`, `skills/pickup/SKILL.md`, `skills/fresh/SKILL.md`;
- `rules/conventions.md`.

Tests (the acceptance oracle) live in `plugins/handover/tests/`: `fm` = `fresh-marker.test.js`,
`ssc` = `session-start-context.test.js`.

## Purpose

Work should survive the end of a session, a `/clear` and a compaction. A repository keeps one status
file, `HANDOVER.md`, at its root. Skills write and consume it. A SessionStart hook puts the right
pointer into a fresh context. A one-shot marker lets the hook recognise a `/clear` that the user
started through the fresh skill.

## Interface

**Runtime.**
- Node.js, CommonJS, built-in modules only.
- No child processes, in the hook or in the marker script.

**`scripts/fresh-marker.js` as a module.** The hook loads it with `require`. These export names are
pinned by the tests:

| Export | Contract |
|---|---|
| `markerPath(root)` | absolute path of the marker for a repository root |
| `findRoot(dir)` | repository root containing `dir` |
| `markerTrusted(stat, uid)` | boolean trust decision for a stat-like object |
| `markerFresh(createdAt, now)` | boolean age decision |
| `MARKER_MAX_AGE_MS` | number: twelve hours in milliseconds |

Additional exports are allowed.

**`scripts/fresh-marker.js` as a command.**
- `node fresh-marker.js [dir]` arms the marker for the repository containing `dir` (default: the
  working directory).
- Exit 0 on success, non-zero on failure. The failure reason goes to stderr.

**`hooks/hooks.json`.**
- Registers the hook script for the `SessionStart` event, sources `startup`, `resume`, `clear` and
  `compact`.
- Runs it with `node`, through a path based on `${CLAUDE_PLUGIN_ROOT}`.

**Hook I/O.**
- Stdin: one JSON object. The hook uses `source` (missing means `startup`) and `cwd` (falls back to
  the process directory).
- Stdout: either nothing, or exactly one JSON object with this shape (ssc:38-42):
  `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <text>}}`.
- Exit code: always 0.

## Behaviour

### Marker module

**`findRoot(dir)`**
- Returns the closest directory, starting at `dir` itself, that contains a `.git` entry. The entry
  may be a directory or a plain file (fm:39-54).
- Returns `dir` when no such directory exists above it (fm:56-61).
- Paths are handled lexically: symbolic links are never resolved, so the result keeps the caller's
  spelling of the path (fm:44, where the temp path sits under a symlinked directory on macOS).

**`markerPath(root)`**

| Property | Test |
|---|---|
| Deterministic for a root | fm:23-25 |
| Insensitive to a trailing separator | fm:26 |
| Different for different roots | fm:29-31 |
| Parent directory equals `os.tmpdir()` | fm:35 |
| Base name is `claude-fresh-` + 16 lowercase hex digits + `.json` | fm:36 |
| Base name depends only on the root, not on the temp directory | ssc:28-30 |

The hash function is free.

**`markerTrusted(stat, uid)`**
- `stat` is an object with `uid`, `mode` and `isFile()`.
- Not trusted: a missing `stat`, or one that is not a regular file (fm:87-90).
- An explicit `uid` of `null` disables the owner and mode checks (fm:92-95).
- When the `uid` argument is omitted, the current process user is used (no check on Windows).
- Otherwise trusted exactly when the owner equals `uid` and the file is writable by neither group nor
  others. Required cases (fm:71-85):

| Owner | Mode | Trusted |
|---|---|---|
| the user | 0600 | yes |
| the user | 0644 | yes |
| another user, or root | 0600 | no |
| the user | 0620 | no |
| the user | 0602 | no |
| the user | 0666 | no |

**`markerFresh(createdAt, now = Date.now())`** (fm:97-105)
- True only for a finite number with `now - createdAt` in the range `[0, MARKER_MAX_AGE_MS)`.
- Timestamps in the future fail, however far ahead.
- Non-numbers fail, and so do `NaN` and `Infinity`.

**Arming** (fm:119-140, ssc:256-263)
- The marker is a JSON object with a numeric `createdAt` in epoch milliseconds.
- It contains no key naming a file to read; in particular no `handover` key.
- On POSIX its permission bits are exactly 0600.
- A symbolic link already at the marker path is replaced by a regular file, and the link target
  keeps its content.
- No temporary file is left in the temp directory.

### SessionStart hook

The root is `findRoot(cwd)`, and the handover is `<root>/HANDOVER.md`. Printed paths are absolute.

**Fresh resume.**
- Applies when `source` is `clear` and all of these hold:
  - the marker for the root is trusted;
  - it parses to an object;
  - its `createdAt` is fresh;
  - the handover file exists.
- The context then contains:
  - `Continuing from <handover path>` (ssc:195);
  - `Context was cleared with /fresh` (ssc:74);
  - the handover reduced to its preamble plus the sections whose `## ` heading begins with
    `Next action`, `Open questions`, `Threads` or `Traps` (ssc:75-79);
  - an instruction to check the recorded repository state against reality before carrying out the
    next action.
- In the reduced handover:
  - other sections, `## Follow-ups` for instance, are absent (ssc:79);
  - each kept heading is still followed directly by its own first line (ssc:76);
  - the text is capped at 4000 characters, as the kept README states, with a note when it is cut.
- The marker can be used only once: after the first such `clear`, the next one gets no fresh-resume
  context (ssc:63-88).

**Reminder after compact or resume** (sources `compact` and `resume`).
- Active plan:
  - candidates are the `<root>/docs/plans/*.md` files, `README.md` excluded, whose front-matter
    `status` is not `done` or `abandoned`;
  - among the candidates, the most recently modified wins;
  - a finished plan is never named, even when it is newer (ssc:124-137);
  - when no candidate exists, fall back to the newest `<root>/.planning/*-plan.md`.
- Active ledger: the newest `<root>/.claude/runs/*.json`. Files elsewhere, such as
  `.claude/tasks.json`, are never named (ssc:130-139).
- When a plan or ledger exists, the hook emits a line that:
  - begins with `Before continuing:`; for `compact` this is the start of the whole context
    (ssc:159);
  - contains `re-read the plan <path>;` for the plan (ssc:136);
  - contains `read the task ledger <path>;` for the ledger (ssc:138).

**Pickup hint** (every source except `compact`).
- When the handover exists, the hint contains `<handover path> exists` and `/pickup` (ssc:140-141).
- It must not contain `Next action` (ssc:86-87).
- For `compact`, the word `pickup` appears nowhere in the context (ssc:161).

**Fallback.** A `clear` without a usable marker behaves like `startup`, whatever the reason:
- no marker;
- a stale or future `createdAt` (ssc:103-115, ssc:212-223);
- a writable-by-others marker (ssc:225-241);
- a symlinked marker (ssc:243-254);
- no handover file (ssc:90-101, ssc:201-210).

**Silence.** With nothing to report, stdout is empty (ssc:164-169).

### Skills

All three skills have `name` and `description` in their front matter. How they are worded and
structured is free. The handover skill accepts an optional focus argument, `/handover [focus]`, as
the kept README documents.

**Requirements that tie the skills to the hook:**
- the handover lives at the repository root as `HANDOVER.md`, and there is only one per repository;
- it has a short preamble and sections whose `## ` headings begin with `Next action`, `Threads`,
  `Open questions` and `Traps`, because the hook extracts exactly those;
- the fresh skill arms the marker by running `scripts/fresh-marker.js` (via `${CLAUDE_PLUGIN_ROOT}`)
  for the repository root, then tells the user to clear the context and send one more message.

**What each skill achieves:**

| Skill | Achieves |
|---|---|
| handover | the file brings a memoryless session up to speed: current state taken from real commands, open threads, questions with recommendations, and one runnable next action. Existing content that is still relevant survives a rewrite |
| pickup | work resumes from the file. Before acting, mismatches between the file and the actual repository and PR state are reported. A blocking open question is asked instead of guessed |
| fresh | the user's next prompt survives a `/clear`: it becomes the handover's next action and is resumed automatically through the hook |

**Kept-README facts the skills must keep true:**
- the forge checks are skipped when the forge CLI is missing;
- the skills trigger on the three phrases the README lists for them (wrapping up, continuing where
  the user left off, clearing the context and then continuing).

**Hard limits:**
- no secrets or customer data in the handover;
- the handover is never committed without the user asking;
- issues on the forge are created only after the user agrees.

### Conventions document

`rules/conventions.md` is written freely. It must agree with the hook and the skills, and it must
cover every item that the kept README's Conventions section (README:61-70) attributes to it:
- one handover per repository at the root, updated in place, with git history as its archive, and
  briefings or onboarding documents not counting as handovers;
- dated plans under `docs/plans/` with a front-matter `status` that uses `done` and `abandoned` for
  finished plans;
- ledgers under `.claude/runs/`, worktrees under `.claude/worktrees/`, and private data in a
  `.claude/private/` directory that ignores itself;
- follow-ups as forge issues labelled `follow-up`, which the handover links instead of listing;
- re-reading the plan and the ledger after a compaction or a resume;
- a project's own `CLAUDE.md` taking precedence where it disagrees.

## Errors

- Stdin that is not JSON, or JSON that is not an object (for example `null` or `42`), gives exit 0
  with empty stdout and stderr (ssc:171-179).
- Any internal failure also gives exit 0 with no output.

## Security

- The marker sits in a directory other local users may write to, so it is untrusted input:
  - only a regular file is read, and a symbolic link is never followed (ssc:243-254);
  - the trust decision and the read concern the same file object;
  - opening the marker cannot block the hook;
  - its content never decides which file gets injected; that is always the root's `HANDOVER.md`
    (ssc:184-210).
- Once the hook has read a marker the current user owns, it deletes it, whether or not the marker
  was honoured. A marker owned by another user is left in place.

## Test-pinned items

- The five export names and their contracts (fm:8, fm:64).
- The marker name, location, mode and content (fm:33-37, fm:119-140).
- The hook output shape (ssc:38-42).
- The context fragments quoted above.
- The extracted and excluded handover sections (ssc:75-79).
- Silent exit 0 on bad input (ssc:171-179).

## Amendments (rev 4)

These amendments take precedence over the sections above where they differ.

1. **Arming the marker.** The fresh skill runs the marker script without a directory argument. The
   script then works from its own process working directory, and the skill states that this is the
   session's project directory. How the hook finds its root lexically does not change.
2. **No noise on failure.** Any internal failure of the SessionStart hook gives exit code 0 and
   prints nothing. That includes a failure to load its own module and a stdout that is already
   closed.
3. **Code fences.** A line beginning with `## ` that sits inside a fenced code block is content, not
   a heading.
4. **Trust check arguments.** `markerTrusted(stat, undefined)` behaves exactly like a call that
   leaves the uid out, so the current user is expected. Only an explicit `null` turns the ownership
   checks off.
5. **Hook registration.** `hooks/hooks.json` uses the exec form (`command` is `node`, the script path
   goes in `args`) and sets `timeout` to 10 seconds.

## Amendments (rev 5)

1. **Arming in the right repository.** Before it arms the marker, the fresh skill returns the shell to
   the session's project directory (the repository whose `HANDOVER.md` it just wrote). After arming it
   compares the root named in the script's success line with that repository. A different root counts
   as a failed arm and is reported the same way.

## Amendments (rev 7)

These replace rev 5, amendment 1.

1. **No directory change before arming.** The fresh skill runs the bare marker command in the shell's
   current directory; it does not `cd` to a root printed by git or anything else first.
2. **Same-file check.** The arm counts as successful only when `<root from the success line>/HANDOVER.md`
   is the same file as the `HANDOVER.md` the skill just wrote, compared by file identity (for example
   `test A -ef B`), never as strings. That comparison holds across symlinks, letter case and path
   separators. Any other outcome is a failed arm: the skill says so and tells the user to continue with
   `/pickup` after `/clear`.
3. **Quoting.** A path the skill puts into a shell command is single-quoted, with any single quote in
   it escaped.
4. **Tests** run the whole sequence: a repository reached through a symlink, the marker armed from the
   symlinked directory with `PWD` set as a shell sets it, then the hook run with `source: "clear"` and
   the symlinked `cwd`, which must resume (`Continuing from`). A marker armed for another repository
   must not resume. Assertions go against the hook, not against the script's own output. Tests that
   pin the replaced rev 5 wording may be removed.

## Amendments (rev 8)

1. **Any spelling of the root.** On `source: "clear"` the hook looks for the marker under the root as it
   finds it lexically, and, when that finds none, also under the same root with symlinks resolved.
   Both candidates go through the same trust and freshness checks; the first trusted, fresh marker
   wins and is deleted. So a marker armed from the resolved path resumes a session whose `cwd` is the
   symlinked spelling, and the other way round.
2. **No directory change while writing.** The fresh skill writes the handover and arms the marker
   without changing the shell's directory at any step.
3. **Instructions follow the outcome.** After a successful arm the skill gives the `/clear` + any
   message instructions; after a failed arm it gives only the fallback (`/clear`, then `/pickup`).
4. **Tests:** arm from the resolved path and clear through the symlinked `cwd` (resumes); arm from the
   symlinked path and clear through the resolved `cwd` (resumes); a marker for another repository
   still never resumes.

## Amendments (rev 9)

1. **One canonical spelling when arming.** The marker script arms the marker under the root with
   symlinks resolved, whatever spelling its working directory or `PWD` has. Its success line names
   that resolved root. The hook's two lookups (rev 8, amendment 1) stay, so a marker armed this way
   resumes a `clear` whose `cwd` uses either spelling.
2. **Single use across spellings.** When the hook honours a marker, it also removes a marker of the
   same root under the other spelling, with the same ownership and same-file checks it uses for the
   honoured one. A second `clear` under either spelling then gets no fresh-resume context.
3. **Tests** (normal tests, not `todo`): arm through a shell from the symlinked directory (`PWD` set as
   a shell sets it) and clear through the resolved `cwd` (resumes); arm from the resolved directory and
   clear through the symlinked `cwd` (resumes); after one resume, a second `clear` under either spelling
   does not resume. The `todo` test of rev 8 becomes a normal test or is replaced by these.
4. **Reconciled with the kept tests.** The success line keeps the shell's spelling of the root (a
   kept rev 7 test pins it; the skill's same-file check accepts either spelling). Without a directory
   argument the script writes the marker under both the resolved root and the shell's spelling, and
   the marker lists those root names so the hook can remove every copy once one is honoured; the hook
   only removes copies whose directory is the same as the honoured root.

## Amendments (rev 10)

These amendments take precedence over every earlier section and amendment where they differ.

1. **The marker lists no roots.** The marker object holds only `createdAt`. The `roots` list of rev 9,
   amendment 4 is dropped. A `roots` key in a marker that is read is ignored and never used to
   build a path.
   - The marker script still writes a copy under the resolved root and, when it differs, one under
     the shell's spelling (`PWD`), as before.
   - The hook works out both candidate paths itself: the marker path of the lexical root and the
     marker path of the same root with symlinks resolved.
   - When it honours one of them, it removes the marker at the other candidate path as well, provided
     that file passes the same trust check. It never removes anything else.
   - The kept tests that write or expect a `roots` list may be changed to the new behaviour, and only
     in that respect: in `fresh-marker-rev9.test.js` the test that writes `roots: [link, other]` and
     expects the other marker to be kept, plus any other test that writes or reads `roots` (list them
     in the report).
2. **Single link.** `markerTrusted` additionally requires `stat.nlink === 1` when `stat.nlink` is a
   number. A marker with a second hard link is not trusted.
3. **Cutting the reduced handover.** When the reduced handover is longer than 4000 characters it is
   cut at or before the 4000th character, with the note, as before. The cut also satisfies:
   - it never splits a surrogate pair;
   - it never falls inside a fenced code block: when the limit falls inside one, the cut moves to just
     before the fence's opening line;
   - the note follows on its own line.
   A fence is a line whose first non-space characters are three or more backticks or tildes, with at
   most three leading spaces. It is closed by a line of the same character, at least as long, with no
   info string. An info string that itself contains a backtick does not open a backtick fence. A fence
   that is never closed runs to the end of the text.
4. **Alias copy failure.** When the marker script has written the primary copy and then fails to write
   the alias copy, it removes the primary copy again and reports a failed arm. It never leaves a
   usable marker behind while reporting failure.
5. **Tests**, in new test files, each able to fail before the change:
   - the closed-stdout test is replaced by one that fails if the hook writes to a closed stdout
     without guarding it;
   - the EPIPE test asserts which guard handles the error, by making only that guard's path reachable;
   - fences: an info string with a backtick, an indented fence (one to three spaces), a four-space
     indent (not a fence) and an unclosed fence, both for heading detection and for the cut;
   - a cut through an emoji at the limit;
   - the mtime case of the finished-plan test;
   - a marker owned by another user, at hook level (skipped when not run as root);
   - a marker with `nlink` 2 is not honoured;
   - the alias failure of amendment 4;
   - the rev 4 amendment 2 and 3 tests assert behaviour (exit code, empty output, which lines count as
     headings), not wording.
6. **One marker copy.** Without a directory argument, the marker script writes exactly one marker:
   under the root with symlinks resolved. It no longer writes a second copy under the shell's
   spelling. This replaces the "both spellings" part of rev 9, amendment 4 and of amendment 1 above.
   - Its success line still names the shell's spelling of the root (the kept rev 7 test pins it).
   - Because the hook looks under the lexical root and under the resolved root (rev 8, amendment 1),
     the single marker is found whether the `clear` comes through the symlinked or the resolved
     `cwd`. After it is honoured, no marker for that root is left, so a second `clear` under either
     spelling does not resume, whatever the order of arming and clearing.
   - Amendment 4 (alias copy failure) no longer applies, because there is no alias copy. Its tests
     are replaced by a test that arming leaves exactly one marker file for the root.
   - Kept tests that expect a marker copy under the shell's spelling after a bare arm, and the rev 9
     single-use test that K7 adjusted, may be changed to the single-copy behaviour. List each change.
   - With a directory argument the script behaves as before.
7. **Canonical spelling.** Wherever the marker script or the hook resolves symlinks to get "the root
   with symlinks resolved", it uses the operating system's canonical spelling of the path (on macOS
   this corrects letter case), falling back to the plain resolution when that is unavailable. A bare
   arm from a shell whose `PWD` has the wrong letter case, on a case-insensitive volume, is resumed by
   a `clear` whose `cwd` has the on-disk spelling. Test it where the temp volume is case-insensitive,
   and skip it otherwise.
8. **Fences found once.** Fenced code blocks are found once on the reduced handover's lines, before any
   trimming, and that result serves both heading detection and the cut. Trimming never turns a
   non-fence (for example a four-space-indented run of backticks) into a fence.
9. **Tidy-ups.** In the marker script the success-line write sits on its own line. The rev 10 test that
   loops over a one-element list asserts directly on the resolved-root marker. The final report lists
   every change to a kept test made under amendment 6.
